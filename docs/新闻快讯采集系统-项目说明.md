## 一、项目概述

定时采集两个平台（深潮 TechFlow、Odaily 星球日报）的最新快讯，经过去重、异步解耦，最终存入 MySQL，并通过 FastAPI 对外提供查询接口。

### 验收标准（4 条）

1. 能成功获取两个平台的最新快讯
2. 接口默认返回聚合后的最新 20 条快讯
3. 数据能经过 Kafka 异步写入 MySQL
4. Docker 可以一键启动完整服务

## 二、整体架构与数据流

```
┌─ 深潮 API ─────────┐        ┌────────── 采集器 collector ──────────┐
│ api.techflowpost.com│──每3s──►│ 1.请求接口  2.解析成统一字段           │
└────────────────────┘        │ 3.Redis 初次去重 (source + url)       │
┌─ Odaily API ───────┐        │ 4.标题归一化二次去重                  │
│ web-api.odaily.news │──每3s──►└─────────────────┬────────────────────┘
└────────────────────┘                            │ 新快讯(JSON)
                                           ┌──────▼──────┐
                                           │ Kafka topic  │  ← 异步缓冲
                                           └──────┬──────┘
                                           ┌──────▼──────────┐
                                           │ consumer 消费   │──► MySQL
                                           └─────────────────┘
                                           ┌─────────────────┐
                                           │ FastAPI 查询    │──► GET /api/news/latest?limit=20
                                           └─────────────────┘
```

**为什么用 Kafka？** 采集（每 3 秒）是短平快任务，入库是相对慢的写操作。中间加 Kafka 让两者解耦：采集端发完即返回，即使 MySQL 暂时变慢，消息在 Kafka 排队，消费者慢慢消化，互不拖累 —— 这就是「异步写入」。

## 五、两个平台的接口调研（关键）

两个平台都没有公开文档，接口需通过浏览器 F12 → Network → XHR 抓包定位。

### 深潮 TechFlow

- 接口：`https://api.techflowpost.com/api/client/newsflashes?page={n}&page_size={n}`
- 响应：`{"data": [...], "total": 116086, "page": 1, "page_size": 9}`

| 统一字段 | 来源字段 | 处理 |
|----------|----------|------|
| source | 固定值 | `"techflowpost"` |
| title | `title` | 直接取 |
| content | `abstract` | 直接取 |
| published_at | `created_at` | ISO 字符串 `"2026-09-11T01:07:09.333Z"` → datetime |
| url | `url` | 为空时拼 `https://www.techflowpost.com/newsletter/{id}` |
| collected_at | 无 | 采集时的当前时间 |

### Odaily

- 接口：`https://web-api.odaily.news/newsflash/page?page={n}&size={n}&groupId=0&isImport=false`
- 响应：`{"code":200, "data":{"list":[...], "total":373652, "hasMore":true}, "success":true}`

| 统一字段 | 来源字段 | 处理 |
|----------|----------|------|
| source | 固定值 | `"odaily"` |
| title | `title` | 直接取 |
| content | `description` | **含 `<p>` 标签，需正则去标签** |
| published_at | `publishTimestamp` | **毫秒时间戳** → datetime |
| url | `newsUrl` | 为空时拼 `https://www.odaily.news/newsflash/{id}` |
| collected_at | 无 | 采集时的当前时间 |

## 六、核心模块详解

### 1. 采集器（collectors/）

每个平台独立一个类，`fetch()` 返回统一的 `NewsFlash` 列表。统一字段结构：

```text
source        来源平台
title         标题
content       快讯内容
published_at  发布时间
url           原文链接
collected_at  采集时间
```

### 2. 去重（dedup.py）—— 两级去重

**初次去重（Redis）**：`SETNX key="{source}:{url}"`，返回成功即为新快讯。

**二次去重（标题）**：归一化标题（去空白/标点、英文转小写）后精确匹配。

```python
def normalize_title(title):
    return re.sub(r"[\W_]+", "", title).lower()
```

> 已知边界：精确匹配无法合并跨语言同源新闻（深潮英文标题 vs Odaily 中文标题描述同一事件）。

### 3. Kafka 生产/消费

- 生产者：`flash.to_dict()` → JSON（`ensure_ascii=False` 保留中文）→ 投递 `newsflash` topic。
- 消费者：消费后写 MySQL，**幂等**（依赖 `UNIQUE(source, url)` + 捕获 `IntegrityError` 跳过重复）。

### 4. 数据模型（models.py）

```sql
newsflash (
  id           INTEGER PK AUTO_INCREMENT,
  source       VARCHAR(32)  NOT NULL,
  title        VARCHAR(512) NOT NULL,
  content      TEXT         NOT NULL,
  published_at DATETIME     NOT NULL,
  url          VARCHAR(512) NOT NULL,
  collected_at DATETIME     NOT NULL,
  UNIQUE (source, url),
  INDEX (published_at)
)
```

### 5. 查询接口（api.py）

```
GET /api/news/latest?limit=20
```

按 `published_at DESC` 查询，返回：

```json
{
  "total": 20,
  "items": [
    {
      "source": "odaily",
      "title": "快讯标题",
      "content": "快讯内容",
      "published_at": "2026-09-11T01:34:15",
      "url": "https://...",
      "collected_at": "2026-09-11T01:38:51"
    }
  ]
}
```

## 九、难点与踩坑记录

### 难点 1：接口发现 + 字段映射
- 接口无文档，需抓包定位。
- 时间格式不一致（ISO 字符串 vs 毫秒时间戳）。
- Odaily 正文是 HTML 要去标签。
- url 可能为空要兜底拼接。

### 难点 2：去重是「产品决策」
- 「标题相近」怎么定义要自己定（精确匹配 / 模糊相似度）。
- 精确匹配无法合并跨语言同源新闻。

### 难点 3：异步链路可靠性
- 消费端要幂等，靠 `UNIQUE(source, url)` + 捕获 `IntegrityError` 兜底。

### 难点 4：Docker 编排（实际踩的坑）
1. **Kafka 镜像**：`bitnami/kafka:3.9` 标签不存在 → 改用 `apache/kafka:3.9.0`（KRaft 无 Zookeeper）。
2. **MySQL 索引超长**：`(source, url VARCHAR(1024))` 唯一索引超 InnoDB 3072 字节限制 → url 缩到 512。
3. **Kafka 健康检查**：`kafka-topics.sh` 不在 PATH → 用绝对路径 `/opt/kafka/bin/kafka-topics.sh`。
4. **端口冲突**：本机 3306 被占 → 内部服务不映射宿主机端口。

### 难点 5：测试隔离中间件
- 单测用 `FakeRedis`（内存版）、SQLite 内存库 + `StaticPool`、FastAPI `dependency_overrides` 注入测试会话，不依赖真实 Kafka/Redis/MySQL。

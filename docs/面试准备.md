# 面试准备文档 · 新闻快讯采集系统

> 项目仓库：https://github.com/zhangzeqing1/newFetch
> 技术栈：Python / FastAPI / MySQL / Redis / Kafka / Docker Compose / SQLAlchemy / Alembic / pytest

---

## 一、项目概述（1 分钟自我介绍模板）

> 我做的是一个**多平台实时快讯采集系统**。它定时并发轮询 4 个数据源（深潮、Odaily 两个快讯站，Binance、Upbit 两个交易所公告），把异构的接口响应解析成统一的字段结构，经过 **Redis 两级去重**后投递到 **Kafka**，由消费者**异步写入 MySQL**，最后通过 **FastAPI** 对外提供查询接口。整套服务用 **Docker Compose** 编排，包含 mysql、redis、kafka、采集器、消费者、FastAPI 六个服务，并配了 pytest 单测。核心亮点是：异步解耦的架构设计、两级去重、消费幂等、以及把端到端延迟从 ~2.6s 优化到 ~1s 的并发改造。

**一句话总结架构**：`采集 → 解析 → Redis 去重 → Kafka 解耦 → 消费入库 → FastAPI 查询`

## 二、项目架构问题（必问）

### 2.1 整体数据流是怎样的？

```
[采集器 collector] --并发轮询--> 深潮/odaily/binance/upbit 四个接口
        │  解析成统一字段: source/title/content/published_at/url/collected_at
        ▼
[Redis 去重] ① source+url 初次去重  ② 标题归一化二次去重
        │ 新数据
        ▼
[Kafka topic: newsflash]
        │
        ▼
[消费者] 幂等写入 → [MySQL newsflash 表]
        ▲
[FastAPI] GET /api/news/latest?limit=20 按 published_at 倒序返回
```

### 2.2 为什么用 Kafka？（高频考点）

**核心：异步解耦 + 削峰。**

- **解耦**：采集（生产）和入库（消费）是两个独立进程，通过 Kafka 解耦，互不阻塞。采集端发完即返回，即使 MySQL 暂时慢/挂，消息在 Kafka 排队，消费者慢慢消化。
- **削峰**：如果某时刻突然来了一大批新快讯，不会直接压垮 MySQL，Kafka 起到了缓冲作用。
- **异步**：题目明确要求「数据能经过 Kafka 异步写入 MySQL」，符合需求。
- **可扩展**：以后可以加多个消费者组（比如一个入库、一个发通知），互不影响。

**追问：不用 Kafka 会怎样？** 采集直接写 MySQL 的话，采集节奏被 MySQL 写入耗时拖慢，且两者耦合，MySQL 挂掉会直接影响采集。

### 2.3 为什么用 Redis 做去重？（高频考点）

- **快**：Redis 是内存数据库，单次操作微秒级，能扛住高频轮询的去重。
- **原子性**：`SETNX`（SET if Not eXists）是原子的，天然适合「判断是否存在 + 写入」的去重场景，不会并发时重复。
- **简单**：用 key-value 或 set 就能表达「已见过」的状态。

### 2.4 去重具体怎么做的？（本项目重点）

做了**两级去重**：

1. **初次去重（Redis）**：按 `source + url` 去重。
   ```python
   # SETNX：key 不存在才写入，返回 True 表示新数据
   redis.set(f"newsflash:url:{source}:{url}", "1", nx=True)
   ```
2. **二次去重（标题）**：聚合多平台数据后，标题归一化（去空白/标点、英文转小写）再精确匹配，用 Redis Set 的 `SADD` 去重，拦截跨平台的重复新闻。

**追问：为什么两级去重？** 一级是按链接去重（同一平台重复），二级是按标题去重（不同平台报道同一事件、链接不同但标题相近）。

### 2.5 如何保证消息「不重复消费」？（幂等性）

消费端做**幂等**：MySQL 表加了唯一约束 `UNIQUE(source, url)`，消费者写入时捕获 `IntegrityError`，重复消息直接跳过。

```python
try:
    session.add(flash); session.commit()
except IntegrityError:
    session.rollback()   # 重复，跳过
```

### 2.6 如何保证消息「不丢失」？

（本项目是简化版，重点是理解 Kafka 的可靠性机制）
- **生产者**：`acks=all`（等所有副本确认才返回）+ 重试。
- **Broker**：`replication_factor > 1`（多副本冗余）。
- **消费者**：手动提交 offset（处理完再提交，而不是自动提交）。

### 2.7 延迟是怎么优化的？（亮点，重点讲）

初始是「顺序采集 + 3 秒间隔」，一轮周期 ~5 秒。优化成「**并发采集 + 1 秒间隔**」：

- 用 `ThreadPoolExecutor` 让 4 个站**同时**发请求，一轮耗时从「4 站之和 ~2.2s」降到「最慢那站 ~0.6s」。
- 轮询间隔从 3s 降到 1s。
- 结果：端到端延迟从平均 ~2.6s 降到 **~1s**。

**追问：为什么用线程而不是 asyncio？** 采集是 I/O 密集（等网络响应），线程和协程收益相同；线程池只改主循环一个文件，不用重写采集器、不加依赖。若要用协程则需 aiohttp 全量改写。

**追问：还能更快吗？** 上 WebSocket 推送（Binance 有公开 `com_announcement` 流）+ 部署到海外 VPS 就近采集，能到亚秒级。但公告是人工发布的，源站侧本身有分钟级延迟，再快意义有限。

### 2.8 Docker 编排怎么做的？

6 个服务：`mysql` / `redis` / `kafka`(KRaft 单节点) / `collector` / `consumer` / `fastapi`，外加一次性 `migrate`（跑 Alembic 建表后退出）。

关键点：
- **依赖顺序**：用 `depends_on` + `condition: service_healthy`（healthcheck）保证 MySQL/Redis/Kafka 就绪后才启动业务服务。
- **建表**：`migrate` 服务执行 `alembic upgrade head`，`fastapi`/`consumer` 依赖它 `service_completed_successfully`。

### 2.9 测试怎么做的？

用 **mock/假对象隔离中间件**，不依赖真实 Kafka/Redis/MySQL：

- 解析测试：mock `requests.get` 返回固定 JSON，验证字段映射。
- 去重测试：写一个内存版 `FakeRedis`（实现 `set`/`sadd`）。
- Kafka 测试：验证序列化/反序列化（中文不转义）。
- API 测试：SQLite 内存库 + `StaticPool`（共享连接）+ FastAPI `dependency_overrides` 注入测试会话。

### 2.10 踩过的坑（能体现工程经验）

1. **MySQL 索引超长**：`(source, url VARCHAR(1024))` 唯一索引在 utf8mb4 下超 InnoDB 3072 字节限制，报错 `1071 Specified key was too long` → url 缩到 512。
2. **Kafka 镜像**：`bitnami/kafka:3.9` 标签不存在 → 换 `apache/kafka:3.9.0`（KRaft 无 Zookeeper）。
3. **健康检查**：`kafka-topics.sh` 不在 PATH → 用绝对路径。
4. **端口冲突**：本机 3306 被占 → 内部服务不映射宿主机端口，只暴露 FastAPI 8000。

## 三、MySQL 扩展知识

### 3.1 三大范式（必考）

| 范式 | 要求 | 反例 |
|------|------|------|
| **1NF** | 每个字段原子性，不可再分 | 一个字段存 "标题1,标题2" |
| **2NF** | 在 1NF 基础上，非主键字段**完全依赖主键**（消除部分依赖，针对联合主键） | 主键 (订单id,商品id)，却只依赖订单id 的字段 |
| **3NF** | 在 2NF 基础上，非主键字段**不传递依赖**于主键 | 存了「分类名」又存「分类的创建人」 |

**结合本项目**：`newsflash` 表字段都直接描述一条快讯本身（source/title/content/published_at/url/collected_at），没有冗余，符合 3NF。

**追问：为什么有时要反范式（冗余）？** 为了查询性能，用空间换时间，减少 join。比如要频繁查「分类名」，就冗余存一份，避免每次 join 分类表。

### 3.2 索引（必考）

- **B+ 树**：MySQL InnoDB 默认索引结构。所有数据存在叶子节点，叶子节点用链表相连，适合范围查询。
- **为什么用 B+ 树不用 B 树/哈希**：B+ 树非叶子节点不存数据、更矮胖（减少磁盘 IO）；叶子节点有序+链表，支持范围查询和排序。哈希索引只支持等值查询。
- **最左前缀原则**：联合索引 (a,b,c)，查询用 a 或 a,b 或 a,b,c 才走索引，只查 b 不走。
- **覆盖索引**：查询的列都在索引里，不用回表。
- **本项目**：`published_at` 建了索引，因为查询要按它倒序排序。

### 3.3 事务与隔离级别（常考）

ACID：原子性、一致性、隔离性、持久性。

隔离级别（从低到高）：
1. **读未提交**（脏读）
2. **读已提交**（不可重复读）
3. **可重复读**（MySQL 默认，幻读 —— InnoDB 用 MVCC + 间隙锁解决大部分）
4. **串行化**（性能最差）

MVCC（多版本并发控制）：通过版本链 + ReadView 实现快照读，不加锁也能读一致数据。

### 3.4 InnoDB vs MyISAM

- InnoDB：支持事务、行级锁、外键、崩溃恢复，**MySQL 5.5+ 默认**。
- MyISAM：不支持事务、表级锁，查询快但写并发差，已淘汰。

## 四、Redis 扩展知识

### 4.1 为什么 Redis 单线程还这么快？（多路复用，必考）

**单线程**指的是「命令执行」单线程，但它用 **I/O 多路复用**处理大量并发连接：

- 传统阻塞 I/O：一个连接一个线程，`read` 阻塞等待数据，连接多了线程爆炸。
- **I/O 多路复用**（epoll）：一个线程同时监听多个 socket，只有「就绪」的 socket 才处理。通过 `epoll_wait` 返回就绪的事件列表，逐个处理。这样单线程就能管理成千上万连接。
- 加上**内存操作**、高效数据结构，所以很快。

**核心**：Redis 快不是因为单线程，而是「内存 + 多路复用 + 避免锁开销」。

### 4.2 SETNX 与去重（结合项目）

`SET key value NX`：只有当 key 不存在时才设置成功，返回成功=新数据。**原子性**保证并发下不会重复写入，所以适合去重。

### 4.3 常用数据结构

| 结构 | 场景 |
|------|------|
| String | 缓存、计数器（本项目 url 去重 key） |
| Hash | 对象存储 |
| List | 消息队列、最新列表 |
| **Set** | 去重、交并差集（本项目标题去重用 SADD） |
| ZSet | 排行榜、按分数排序 |

### 4.4 持久化

- **RDB**：快照，某个时间点全量内存 dump 到磁盘。恢复快，但两次快照间的数据会丢。
- **AOF**：追加写命令日志。数据更安全，可配置 `appendfsync always/everysec/no`。
- 生产常用：RDB + AOF 结合。

### 4.5 缓存三大问题（高频）

| 问题 | 场景 | 解决 |
|------|------|------|
| **穿透** | 查不存在的 key，每次都打到 DB | 缓存空值 / 布隆过滤器 |
| **击穿** | 热点 key 过期瞬间大量请求打 DB | 互斥锁 / 逻辑过期 / 永不过期 |
| **雪崩** | 大量 key 同时过期，DB 被压垮 | 过期时间加随机值 / 多级缓存 |

### 4.6 过期策略 + 内存淘汰

- 过期：惰性删除 + 定期删除结合。
- 淘汰：`allkeys-lru`（常用）、`volatile-lru` 等，内存满时按策略淘汰。

## 五、Kafka 扩展知识

### 5.1 核心概念（必考）

- **Topic**：消息分类，逻辑概念。
- **Partition（分区）**：Topic 的物理切分，每个分区是一个有序、不可变的消息队列。
- **Consumer Group（消费者组）**：组内消费者分摊消费不同分区；组间互不影响（广播）。
- **Broker**：Kafka 服务节点。
- **Offset**：消息在分区内的位置。

### 5.2 分区有什么用？

1. **并行度**：一个分区只能被组内一个消费者消费，分区数决定并行上限。
2. **顺序性**：同一分区内消息有序（本项目单分区即可保证顺序）。
3. **水平扩展**：数据分散到多台机器。

### 5.3 消息可靠性：不丢 + 不重（高频）

**不丢**：
- 生产者 `acks=all` + 重试。
- 副本 `replication_factor > 1`，`min.insync.replicas` 控制最少同步副本。
- 消费者**处理完再手动提交 offset**（而非自动提交）。

**不重**：
- 消费者做幂等（本项目用唯一约束 + 捕获冲突）。
- Kafka 也提供「幂等生产者」（`enable.idempotence`）。

### 5.4 为什么 Kafka 吞吐高？

1. **顺序写磁盘**：追加写，比随机写快很多（利用磁盘顺序写接近内存速度）。
2. **零拷贝**：用 `sendfile` 直接把磁盘数据传到网卡，减少内核态/用户态拷贝。
3. **Page Cache**：读写走操作系统页缓存。
4. **批量 + 压缩**：批量发送、消息压缩。

### 5.5 消费者组 Rebalance

组内成员变化（加消费者/挂掉）时，重新分配分区。期间会短暂停止消费，所以会引发「重复消费」，这也是消费端必须幂等的原因之一。

## 六、FastAPI / Web 扩展知识

### 6.1 FastAPI 依赖注入

`Depends(get_session)` 把「获取数据库会话」这个关注点抽离，路由函数只关心业务。好处：可测试（`dependency_overrides` 替换成 SQLite 会话）、可复用。

### 6.2 同步 vs 异步

- FastAPI 里 `def`（同步）跑在**线程池**，`async def`（异步）跑在**事件循环**。
- 本项目查询接口用同步 `def` + SQLAlchemy 同步引擎，简单够用。
- 若换成 `async def` + 异步引擎（aiomysql），能提升高并发下的吞吐。

### 6.3 Pydantic

声明式数据校验/序列化。`response_model` 自动校验并生成 OpenAPI 文档。`from_attributes=True` 支持从 ORM 对象直接转换。

## 七、可能的综合追问 / 场景题

1. **如果某个数据源接口挂了，系统会怎样？** 采集器里每个站独立 try/except，单站失败不影响其他站（并发下更明显），日志记录失败，下轮继续重试。

2. **如果 Kafka 挂了？** 生产者发送失败会报错/重试，采集端不会崩（数据可能暂时丢失，取决于配置）。这是「异步解耦」的代价——需要在可靠性和延迟间权衡。

3. **如果数据量暴涨（比如每秒上千条），怎么扩容？** 提高 Kafka 分区数 + 增加消费者实例（组内分摊）；MySQL 可以分库分表；Redis 集群化。

4. **标题去重用什么算法更准？** 现在是归一化精确匹配。更准可以用 `difflib.SequenceMatcher` 相似度阈值、或文本 embedding + 向量相似度，但都更重、更慢，要权衡。

5. **Redis 挂了去重会失效吗？** 会，去重状态丢失会导致重复入库（但有 MySQL 唯一约束兜底不重复）。生产可用 Redis 主从/AOF 保证状态不丢。

6. **为什么 published_at 存 UTC 而不是本地时间？** 多平台时区不一致（有 +08:00、+09:00、UTC），统一转 UTC 存库，查询排序才准确。展示层再转本地时区。
